## 1. 引言

### 1.1 编写目的
本文档用于明确"合同回款管理系统"在公司内部的业务范围、功能边界、非功能性指标与验收标准，作为后续产品设计、开发、测试、验收以及干系人沟通的统一依据。读者对象包括：业务负责人、产品经理、UI/UX 设计师、研发、测试、运维以及最终用户代表。

### 1.2 项目背景
公司当前的合同与回款管理依赖线下纸质归档、Excel 台账以及邮件沟通，存在以下痛点：
- 合同档案分散，难以集中检索与统计；
- 回款计划与实际到账信息分离，财务对账成本高；
- 合同到期、续签、回款逾期等关键节点缺乏主动提醒；
- 缺少面向管理层的整体经营看板，决策依赖人工汇总。

为解决以上问题，公司决定立项建设一套面向内部多角色协同、Web 端访问的合同与回款一体化管理系统。

### 1.3 范围
本期建设范围聚焦"客户档案"、"合同档案"与"回款过程"三个核心域，不包含审批流、电子签章、发票管理、对外集成等扩展能力（详见 §2.2）。

### 1.4 术语与缩略语
| 术语 | 含义 |
| --- | --- |
| 客户 | 与公司签订合同的对象，是合同与回款的归属主体 |
| 合同 | 公司与客户之间签订的具有金额与履约期限的商务协议 |
| 回款计划 | 按合同约定，对应收款项进行的分期或一次性排期 |
| 实际回款 | 客户已支付并到账的款项记录 |
| 应收账款（AR） | 已签订合同但尚未到账的金额 |
| 账龄 | 应收账款从约定到期日起未收回的时长区间 |
| 软删除 | 通过标记位将记录标记为已删除，但物理数据仍保留 |
| 硬删除 | 物理删除数据库记录，不可恢复 |
| RBAC | 基于角色的访问控制（Role-Based Access Control） |
| SRS | 软件需求规格说明书 |

## 2. 项目概述

### 2.1 产品定位与目标
**一句话定位**：面向公司内部销售、财务及管理层的客户档案、合同档案与回款过程一体化数字化管理平台。

**核心目标**：
1. **合同档案集中化**：实现合同信息与电子档案的结构化存储与多条件检索；
2. **回款过程可视化**：建立"合同 → 回款计划 → 实际回款"完整链路，主动预警逾期；
3. **应收账款可量化**：通过账龄分析与综合看板，向管理层提供统一的经营视图；
4. **协作有迹可循**：通过角色权限与操作日志保障合规与审计可追溯。

### 2.2 系统范围

**本期包含**：
- 客户档案管理（独立主数据，统一被合同与回款引用）
- 合同登记、归档、查询、变更、到期/续签提醒
- 回款计划制定、实际回款登记（含批量录入）、逾期预警、账龄分析
- 综合看板、回款统计报表
- 用户、角色与数据权限管理
- 操作审计日志、敏感字段加密
- 站内消息通知

**本期不包含**（明确排除，避免范围蔓延）：
- 合同审批流（多级审批、电子签章）
- 合同模板与在线起草
- 发票管理、银行流水自动对账
- 客户关系管理（CRM）的高级能力（商机、跟进、销售漏斗等）
- 与 ERP / OA / 财务系统的接口对接
- 多币种与汇率换算
- 移动端 App / 小程序 / 企业微信内嵌
- 邮件、短信、IM 第三方通知

> 上述被排除项可作为二期/三期演进规划的候选，参见 §10.2。

### 2.3 用户角色与权限概览

系统初期规划 5 类角色，基于"角色 + 数据范围"双维度控制访问。

| 角色编号 | 角色名称 | 主要职责 | 数据范围 |
| --- | --- | --- | --- |
| R01 | 销售/业务员 | 登记/维护客户、合同与回款计划，登记实际回款 | 仅本人 |
| R02 | 销售主管 | 查看下属客户、合同与回款数据，跟进团队回款进度，可对合同添加备注 | 本部门 |
| R03 | 财务 | 核对实际回款、跟踪应收账款与账龄、导出统计 | 全公司 |
| R04 | 高管/决策层 | 查看综合看板与统计报表 | 全公司（只读） |
| R05 | 系统管理员（含超级管理员） | 用户、角色、部门、日志维护；执行硬删除 | 全公司（管理） |

> 说明：
> - 本期 **不实现合同审批流**。销售主管以"查看 + 备注"形式参与，不构成阻塞性流程节点；
> - 系统管理员（R05）中的"超级管理员"账户具备执行硬删除的特权，详见 §4.1 与 §5.3；
> - 普通管理员仅可执行常规管理操作，硬删除权限需在角色权限点上单独勾选。

## 3. 业务流程

### 3.1 客户与合同登记归档流程

```
[销售/业务员] 录入/选择客户 → 录入合同基本信息 + 上传扫描件附件
        │
        ▼
[系统] 自动生成合同编号、计算关键节点（到期日：默认提前 30 天提醒）
        │
        ▼
[销售/业务员] 在合同基础上制定回款计划（一次或多期，到期前 7 天提醒）
        │
        ▼
[系统] 合同进入"履行中"状态，启动到期/回款节点提醒
        │
        ▼
[销售主管] 查阅档案，必要时添加备注
        │
        ▼
[销售/业务员] 履约期结束 → 关闭合同 / 续签变更
```

### 3.2 回款执行与对账流程

```
[财务/销售] 客户付款 → 在系统登记"实际回款"（金额/到账日/凭证）
        │
        ▼
[系统] 自动核销对应回款计划期次，更新合同已收/未收金额
        │
        ▼
[系统] 每日扫描超过约定到期日且未足额收款的回款计划 → 生成逾期预警
        │
        ▼
[系统] 通过站内信通知合同负责人、销售主管、财务
        │
        ▼
[财务] 在账龄分析中按 0-30 / 31-60 / 61-90 / 90+ 天分桶查看，跟进催收
```

## 4. 功能需求

> 编号约定：UC-MM-NN，其中 MM 为模块号，NN 为用例序号。每个功能项给出功能描述、操作角色与关键规则。

### 4.1 用户与权限管理（UC-01）

| 编号 | 功能 | 描述 | 角色 |
| --- | --- | --- | --- |
| UC-01-01 | 用户登录 | 账号 + 密码登录；连续 5 次失败锁定 15 分钟 | 全员 |
| UC-01-02 | 修改密码 | 强制首次登录修改；密码强度校验（≥8 位，含大小写、数字） | 全员 |
| UC-01-03 | 用户管理 | 增删改查用户，分配所属部门与角色 | R05 |
| UC-01-04 | 角色管理 | 内置 5 类角色；可配置功能权限点（菜单 + 操作按钮 + 硬删除） | R05 |
| UC-01-05 | 数据权限 | 按"本人 / 本部门 / 全公司"三档控制可见数据范围 | R05 |
| UC-01-06 | 硬删除特权 | 超级管理员可对客户、合同、回款记录执行硬删除（物理删除）；操作必须二次确认 + 输入密码 + 强制写入审计日志 | R05（超级管理员） |
| UC-01-07 | 退出登录 | 主动退出 + 会话 30 分钟空闲自动失效 | 全员 |

> 硬删除约束：
> - 默认情况下所有删除均为软删除，仅超级管理员账号在勾选了"硬删除"权限点后可见入口；
> - 硬删除会级联清除关联的子数据（如合同的附件、回款计划、变更记录），需在确认对话框中明确列出影响范围；
> - 硬删除日志单独存档且不可清理，审计可追溯被删除对象的关键字段快照。

### 4.2 客户档案管理（UC-02）

> 设计意图：客户作为 **独立主数据** 被合同与回款共同引用，避免重名混淆，支撑客户维度的账龄统计与风险洞察。

#### 4.2.1 功能列表

| 编号 | 功能 | 描述 | 角色 |
| --- | --- | --- | --- |
| UC-02-01 | 新建客户 | 录入客户基本信息与至少一个联系人 | R01、R05 |
| UC-02-02 | 客户列表 | 多条件筛选与分页查询（见 §4.2.3） | R01–R04、R05 |
| UC-02-03 | 客户详情 | 查看客户全部字段、联系人列表、关联合同与回款汇总 | R01–R04、R05 |
| UC-02-04 | 编辑客户 | 修改客户字段；客户名称变更需写入变更记录 | R01（本部门内）、R05 |
| UC-02-05 | 联系人管理 | 一个客户可维护多个联系人（姓名、职务、电话、邮箱、是否主联系人） | R01、R05 |
| UC-02-06 | 客户合并 | 当发现重复客户时，将 B 客户的合同与回款迁移至 A，并将 B 标记为已合并 | R05 |
| UC-02-07 | 启用/停用 | 停用后不可在新建合同时被选中，但不影响历史合同 | R05 |
| UC-02-08 | 软删除/硬删除 | 软删除：默认操作；硬删除：仅超级管理员，且要求该客户无任何合同 | R05 |
| UC-02-09 | 查重提示 | 新建客户时按名称、统一社会信用代码模糊匹配并提示已有客户 | 系统 |

#### 4.2.2 客户核心字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 客户编号 | 字符串 | 是 | 系统自动生成，规则：CU-YYYYMM-NNNN |
| 客户名称 | 字符串 | 是 | 最大 100 字符；同名将给出查重提示 |
| 客户简称 | 字符串 | 否 | 用于列表展示 |
| 客户类型 | 枚举 | 是 | 企业 / 政府/事业单位 / 个体工商户 / 个人 / 其他 |
| 统一社会信用代码 | 字符串 | 否 | 18 位，企业类型时建议填写 |
| 所在地区 | 级联选择 | 否 | 省/市/区 |
| 详细地址 | 字符串 | 否 | — |
| 行业 | 枚举 | 否 | 可基于公司业务定义 |
| 客户等级 | 枚举 | 否 | A / B / C / D（默认 C） |
| 主要联系人 | 引用 | 是 | 至少 1 名联系人 |
| 负责人 | 用户引用 | 是 | 默认登记人，所属部门由其继承 |
| 状态 | 枚举 | 是 | 启用 / 停用 / 已合并 |
| 备注 | 长文本 | 否 | — |

**联系人字段**：姓名（必填）、职务、电话、邮箱、微信、是否主联系人、备注。

#### 4.2.3 客户列表筛选条件

- 客户编号 / 名称 / 简称 / 信用代码（模糊匹配）
- 客户类型、客户等级、状态（多选）
- 所在地区、行业
- 负责人、所属部门
- 是否有合同（是/否）、是否存在逾期回款（是/否）

#### 4.2.4 关联视图（客户详情页）

- **合同 Tab**：该客户的全部合同列表，含金额、状态、签订日；
- **回款 Tab**：该客户全部回款计划与实际回款汇总；
- **指标卡**：累计签约金额、累计回款金额、待收金额、逾期金额。

### 4.4 回款管理（UC-04）

#### 4.4.1 功能列表

| 编号 | 功能 | 描述 | 角色 |
| --- | --- | --- | --- |
| UC-04-01 | 制定回款计划 | 基于合同金额一次或分期排期，每期含期次/计划日期/计划金额 | R01 |

| UC-04-09 | 应收账款账龄分析 | 按 0–30 / 31–60 / 61–90 / 90+ 天四档统计未收金额，支持按客户/部门钻取 | R03、R04 |
| UC-04-10 | 回款列表查询 | 多条件筛选（合同、客户、负责人、状态、日期区间） | R01–R04、R05 |
| UC-04-11 | 实际回款红冲 | 不可删除，仅可红冲；红冲会反向核销并写入审计日志 | R03 |
| UC-04-12 | 硬删除 | 超级管理员特权操作，需二次确认 + 密码校验 | R05（超级管理员） |

#### 4.4.2 关键业务规则

- 回款计划总金额 = 合同金额（允许误差 ≤ 0.01 元，用于分期凑整）。
- 单期实际回款金额可大于计划金额（视为提前付清后续期次），系统按到期顺序自动核销剩余金额。
- 实际回款一经登记，**不可删除**（仅超级管理员可执行硬删除），常规情况通过"红冲"反向记录冲销，保证审计完整性。
- 计划日期晚于合同到期日的，新建时给予警告但不阻断。
- 逾期天数 = 当前日期 − 计划日期（不足一日按 0 计）。

#### 4.4.3 账龄计算规则

| 账龄区间 | 计算规则 |
| --- | --- |
| 未到期 | 计划日期 ≥ 当前日期 |
| 0–30 天 | 1 ≤ 当前日期 − 计划日期 ≤ 30 |
| 31–60 天 | 31 ≤ 差值 ≤ 60 |
| 61–90 天 | 61 ≤ 差值 ≤ 90 |
| 90 天以上 | 差值 > 90 |

## 5. 数据需求

### 5.1 核心实体关系（ER 概要）

```
[部门 Department]◀── 隶属 ───[用户 User]
       ▲                        │
       │ 所属                   │ 负责
       │                        ▼
[客户 Customer] ──1:N──▶ [联系人 Contact]
       │
       │ 1:N（强关联）
       ▼
[合同 Contract] ──1:N──▶ [合同附件 Attachment]
       │  │
       │  └─1:N──▶ [合同变更记录 ChangeLog]
       │
       │ 1:N
       ▼
[回款计划 PaymentPlan] ──1:N──▶ [实际回款 PaymentRecord]
                                          │
                                          └─0:1──▶ [付款凭证附件]
```

### 5.2 核心实体字段（节选，详见数据库设计文档）

**Customer（客户）**：客户编号、名称、简称、类型、统一社会信用代码、地区、地址、行业、等级、负责人、所属部门、状态（启用/停用/已合并）、合并目标 ID、创建时间、更新时间、是否软删除、备注。

**Contact（联系人）**：客户 ID、姓名、职务、电话（加密）、邮箱（加密）、微信、是否主联系人、备注。

**Contract（合同）**：合同编号、名称、类型、**客户 ID（外键，必填）**、金额（加密）、签订日、履约开始日、履约到期日、提醒提前天数（覆盖系统默认）、负责人、部门、状态、创建时间、更新时间、是否软删除、备注。

**PaymentPlan（回款计划）**：合同 ID、期次、计划日期、计划金额、已核销金额、未核销金额、是否逾期、逾期天数、提醒提前天数（覆盖系统默认）。

**PaymentRecord（实际回款）**：合同 ID、回款计划 ID（核销关系）、到账日期、到账金额、付款方、凭证号（加密）、登记人、登记时间、是否红冲、红冲关联记录 ID、备注。

**ChangeLog（变更记录）**：业务对象类型、业务对象 ID、变更字段、原值、新值、变更原因、操作人、操作时间。

**OperationLog（操作日志）**：操作人、IP、操作模块、操作类型（增/删/改/查/登录/硬删除）、目标对象类型与 ID、关键字段快照（用于硬删除还原审计）、请求参数摘要、结果、时间戳。

### 5.3 数据保留与删除策略

| 删除方式 | 触发者 | 适用对象 | 行为 |
| --- | --- | --- | --- |
| 软删除（默认） | 业务用户 / 普通管理员 | 客户（无合同时）、草稿合同 | 标记 is_deleted=1，进入回收站，可还原 |
| 红冲 | 财务 | 实际回款 | 生成反向记录，保留原始数据 |
| 硬删除（特权） | 超级管理员 | 客户、合同、回款全部对象 | 物理删除并级联子表；写入硬删除日志（含字段快照）；不可恢复 |

- 业务数据（客户/合同/回款）默认 **永久保留**；
- 操作日志保留 ≥ 2 年，**硬删除日志永久保留**；
- 站内信保留 90 天后自动归档；
- 附件文件保留与主记录一致；硬删除时附件同步从对象存储中清理。

## 6. 非功能性需求

### 6.1 性能
- 合同列表、回款列表查询响应时间 P95 ≤ 1.5 秒（数据量 ≤ 10 万条）；
- 综合看板首屏加载 P95 ≤ 2 秒；
- 单文件上传 ≥ 5MB/s（内网环境）；
- 系统支持 ≥ 100 并发用户在线（参考中型规模）。

### 6.2 安全
- **身份认证**：账号密码 + 会话 Cookie，密码采用 bcrypt 加盐存储；
- **权限控制**：RBAC + 数据范围（本人/本部门/全公司）；
- **敏感字段加密**：合同金额、客户联系方式、付款凭证号在数据库中以 AES-256 加密存储；
- **传输加密**：全站强制 HTTPS（TLS 1.2+）；
- **审计日志**：覆盖登录、关键 CRUD、权限变更、附件操作，不可删除；
- **越权防护**：服务端二次校验数据归属，防止 IDOR；
- **基础合规**：满足公司内部信息安全管理办法的基础要求（不强制等保 2.0）。

### 6.3 可用性
- 系统可用性 ≥ 99.5%（每月不可用时间 ≤ 3.6 小时）；
- 关键业务（合同登记、回款登记）出错时给出明确文案，并保留草稿。

### 6.4 兼容性
- 支持最新两个主要版本的 Chrome、Edge、Firefox；
- 最低分辨率 1366×768；
- 不强制支持移动端浏览器（响应式作为加分项）。

### 6.5 可维护性与可扩展性
- 前后端分离架构，便于独立演进；
- 业务模块（合同、回款、报表、通知）边界清晰，预留二期扩展点（审批、发票、集成）。

### 6.6 国际化与本地化
- 本期仅支持简体中文与人民币；
- 所有金额统一以"元"展示，精确到分，使用千分位分隔；
- 时间统一使用 Asia/Shanghai 时区。

## 7. 部署架构与建议

### 7.1 推荐部署方式
鉴于：
- 系统涉及合同金额、客户联系方式等敏感商务信息；
- 公司本期暂无外部协作与移动办公需求；
- 维护成本与合规风险更可控；
- 运维由程序开发团队承担（详见 §10.1），需选择对开发团队友好的部署方案。

**推荐：公司内网（私有化）部署，全栈容器化交付**。

### 7.2 参考部署拓扑

```
                ┌────────────────────┐
   内网用户 ───▶│  反向代理（Nginx） │── HTTPS
                └─────────┬──────────┘
                          │
                ┌─────────▼──────────┐
                │  应用服务器（≥2台）│
                │  前端 + 后端 API    │
                └─────────┬──────────┘
                          │
            ┌─────────────┼─────────────┐
            ▼             ▼             ▼
      ┌──────────┐ ┌────────────┐ ┌────────────┐
      │ MySQL    │ │ Redis(缓存)│ │  对象存储  │
      │（主从）  │ │            │ │（合同附件）│
      └──────────┘ └────────────┘ └────────────┘
```

### 7.3 推荐技术栈（建议性，可调整）
- 前端：React 或 Vue 3 + TypeScript + Ant Design / Element Plus
- 后端：Java（Spring Boot）/ Node.js（NestJS）/ Python（Django/FastAPI），任选其一
- 数据库：MySQL 8.x（主从）
- 缓存：Redis 7.x
- 文件存储：MinIO 或公司内网文件服务器
- 部署：Docker + Docker Compose / Kubernetes，反向代理使用 Nginx
- 运维支撑：自动化备份脚本（每日 1 次，保留 30 天）+ 基础监控（Prometheus + Grafana 可选）+ 日志集中采集（ELK 可选），由开发团队统一负责。

1. **功能验收**：§4 中所列全部功能项通过测试用例验证，缺陷分级遵循公司测试规范，P0/P1 缺陷清零；
